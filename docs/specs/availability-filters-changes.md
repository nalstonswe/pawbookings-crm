# Availability filters: suggested code changes

Companion to [availability-filters.md](availability-filters.md).

The full set of suggested changes is in [availability-filters-changes.patch](availability-filters-changes.patch), a
standard unified diff generated with `git diff` (13 files, +918 / -48) against the base of this branch. The changes
are **suggestions, not applied code**; this branch contains only the documents. To try them on a scratch branch:

```bash
git apply --check docs/specs/availability-filters-changes.patch   # dry run
git apply docs/specs/availability-filters-changes.patch
```

> **Not executed.** The environment used to draft these had neither Ruby nor Node available, so none of the backend
> specs, frontend tests or lint were run. Treat them as a reviewed first draft.

## What each file in the patch does

### Backend

| File | Change |
|---|---|
| `backend/config/routes.rb` | New business-scoped route `GET /api/v1/businesses/:slug/availability_slots`, served by a new controller so the per-service CRUD controller is untouched. |
| `backend/app/controllers/api/v1/businesses/all_availability_slots_controller.rb` (new) | Authorizes with the existing `AvailabilitySlotPolicy#index?` (any member). Resolves `service_id` through `Current.business.service_offerings.find` (404 for another business's service), returns `422 validation_failed` for bad filters, paginates with the shared `Paginatable`, and responds with `slots`, `total_count`, `has_more`. |
| `backend/app/services/availability_slot_filter.rb` (new) | Validates the filters and builds the tenant-scoped relation. Remaining capacity (accepted bookings only, ADR 0005) and the Closed/Full/Limited/Available state are computed in SQL so they are filtered *before* limit/offset. The Limited threshold mirrors `availabilityStatus.js`. |
| `backend/db/migrate/20261124180000_add_business_starts_at_index_to_availability_slots.rb` (new) | `business_id`-led index for the all-services query (existing indexes lead with `service_offering_id`). `db/schema.rb` would be regenerated by running the migration. |
| `backend/spec/requests/api/v1/businesses/all_availability_slots_spec.rb` (new) | Request specs: tenant isolation, future-only, stacked filters, business-time-zone inclusive dates, remaining (not total) capacity, state thresholds, every 422 rule, pagination metadata and ordering, no N+1. |

### Frontend

| File | Change |
|---|---|
| `frontend/src/lib/availabilityStatus.js` | Exposes the state key and label so the filter dropdown and the table share one source of truth with the existing badge. Behavior of `availabilityState` is unchanged. |
| `frontend/src/availability/availabilityFilters.js` (new) | Pure helpers: normalization (one cache key for blank/absent), validation mirroring the server, request params, the `canServeFrom` subset rule, and in-memory `filterSlots` using business-local calendar days. |
| `frontend/src/availability/useFilteredAvailabilitySlots.js` (new) | `useInfiniteQuery` keyed by business slug, normalized filters and role. A complete cached broader result is filtered in memory with no request; a partial one is shown as a placeholder while the server request replaces it. Default `staleTime`/`gcTime`, no explicit invalidation. |
| `frontend/src/availability/AvailabilityFilters.jsx` (new) | The form: single-select service (active services + All), From/To date inputs (`max` = from + 60 days), min remaining capacity, availability state, Submit and Clear filters. Inline client errors plus server 422 details. |
| `frontend/src/availability/AvailabilityOverviewPage.jsx` | Swaps the N-per-service fetch for the new hook, adds the form, two distinct empty states, and a Load more button. The table now shows remaining / capacity and the availability state badge. |
| `frontend/src/availability/availabilityFilters.test.js` (new) | Unit tests for validation, normalization, the subset rule, and in-memory filtering. |

## Choices made where the spec is still open

The spec lists open questions; the code needed *some* answer, so these are placeholders to confirm or change:

| Topic (spec open question) | What the suggested code does |
|---|---|
| Endpoint path (Q9) | `GET /businesses/:slug/availability_slots`; the per-service endpoint and `useAllAvailabilitySlots` are left alone |
| Foreign / invalid IDs (Q2) | Another business's `service_id` is `404`; an unknown `availability_state` is `422` |
| "Future only" (Q3) | `starts_at >= now`, so a slot that has started is excluded |
| 60-day bound (Q11) | A maximum range *length*, not a distance from today |
| Client-side cache reuse (Q1) | In-memory only when the new filter is a subset of the cached one (`canServeFrom`) |
| user/role in key (Q5) | Kept. Logout already calls `queryClient.clear()`, so the role mainly guards a role change in the same session |
| Dashboard (Q6) | Not migrated; it keeps `useAllAvailabilitySlots` |
| Migration (Q8) | Included (`business_id, starts_at` index) |

Other points that go beyond, or differ from, the written spec:

- **`page` is not in the queryKey.** The Load more pattern uses `useInfiniteQuery`, which keeps every page inside one cache entry. The key is `[business slug, normalized filters, role]`.
- **Table columns changed.** It now shows `remaining / capacity` and the availability state badge instead of capacity and Active/Inactive. The spec doesn't say what the table should display, so confirm this.
- **Empty states.** "No slots exist yet" is shown for default filters with no results, which really means "no upcoming slots in the next 60 days".
- **A complete cache is never revalidated** on submit (by design in the spec); a stale `remaining_capacity` is accepted.
